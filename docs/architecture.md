# Архитектура EventMatch 2.0

## Поток запроса

```text
HTML + CSS + JavaScript (/app/)
          │ параметры + свободное пожелание
          ▼
POST /recommend → валидация полей и календаря
          │
          ├─ нет категории в городе → category_not_found
          │                            + проверенные альтернативы по городу
          ▼
Жёсткие фильтры: дата, формат, стартовая цена, язык, длительность
          │
          ├─ нет подходящих → no_matches + причины + проверенные изменения
          ▼
Локальный E5: query → вектор → близость к фрагментам профилей
          │                   (не отменяет обязательные фильтры)
          ▼
85% смысловая близость + 15% запас бюджета → сортировка → TOP 3
          │
          ├─ доказательное объяснение + дословный source span
          ├─ происхождение данных + разбивка баллов
          └─ сравнение с прошлой датой
```

## Хранение и запуск

Исходный каталог — 66 профилей в `backend/data/contractors.jsonl` (содержимое JSON-массив). Он загружается при старте. Отдельной SQL/векторной СУБД нет: для 262 фрагментов достаточно NumPy-матрицы в памяти и JSON-индекса на диске.

`run.py` подготавливает локальную `.venv`, при необходимости скачивает закреплённую модель и запускает FastAPI. Один сервер обслуживает API и frontend. Корень `/` отдаёт health, интерфейс доступен на `/app/`.

## Модель и индекс

`semantic.py` использует multilingual-e5-small, ONNX int8-экспорт Xenova, CPUExecutionProvider. Версия закреплена в `config.py`; файлы и их хеши — в `manifest.json`. Веса лицензированы по MIT.

- Из каждого описания выбираются буквальные фрагменты длиной до 320 символов с `start`/`end`. Приветствия и слишком короткие строки по возможности пропускаются.
- Вход профиля: `passage: <категории>. <точный фрагмент>`; запрос: `query: <пожелание>`.
- Токенизация с лимитом 512, masked mean pooling, L2-нормализация, 384 координаты.
- Сходство — скалярное произведение нормализованных векторов (косинус). Оценка профиля — его лучший фрагмент.
- Индекс инвалидируется отпечатком ID, описаний, категорий, версии алгоритма и модели. Стоимость и занятость не входят в эмбеддинги: их всегда проверяют фильтры.
- Повторные пожелания кэшируются в памяти (до 256); токенизация защищена блокировкой. Запросы не отправляются в сеть.

## Ранжирование и воспроизводимость

При непустом пожелании:

```text
semantic_points = 85 × clamp((cosine − 0.65) / 0.30, 0, 1)
budget_points   = 15 × (1 − price_from_kzt / budget)
total           = semantic_points + budget_points
```

Пороги 0.65/0.30 и веса — фиксированная эвристика. Баллы не являются вероятностью. Без пожелания используется только запас бюджета, вес 100%. Сортировка: итог убывает, цена возрастает, ID возрастает. Фиксированы версия модели и порядок фрагментов, нет случайной генерации. Время ответа вынесено в заголовок, а не JSON. Тесты сравнивают тела повторных ответов на одном окружении; побитовая идентичность вычислений на любых CPU не обещается.

## Объяснения и доверие

`explanations.py` собирает объяснение из пройденных условий и буквальной цитаты. `evidence` содержит исходный текст и позиции, позволяющие проверить `description[start:end] == evidence.text`. Frontend использует текстовые узлы и `<mark>`, не вставляет описание как HTML.

Доступность следует из `busy_dates`; формат, язык и предел часов — из структурированных полей. Разность бюджета и цены означает резерв по стартовой цене, не итоговую смету. При `max_hours = null` услуга по условиям датасета не привязана к часам. Флаги `synthetic`, `price_imputed`, `city_imputed` передаются без изменений. Генеративной LLM нет: новые биографические сведения или обещания не сочиняются, однако достоверность самого исходного описания независимо не проверяется.

## Пустая выдача — проверяемые действия

`alternatives.py` пробует конкретные изменения, каждый раз заново применяя **все** обязательные фильтры. Возвращаются только варианты с хотя бы одним прошедшим кандидатом, его ID, число профилей и минимальная цена.

Порядок: минимальное достаточное увеличение бюджета; ближайшая допустимая дата; сокращение длительности; снятие условия по языку; другой формат. Если одиночных изменений нет, ищется пара дата + бюджет. Для отсутствующей категории проверяется другой город. До трёх предложений, без обещания найти любое возможное сочетание. Исходный запрос не меняется автоматически.

## Сравнение дат

Frontend отправляет `compare_date`, только когда остальные поля совпадают с предыдущим успешным запросом к API. Backend заново получает TOP 3 для прошлой даты и текущих остальных условий. Из предыдущей тройки выделяются ставшие занятыми; из новой — ранее занятые. Это объясняет именно календарные изменения, а не приписывает их AI-модели.

## Интерфейс и ошибки

- Семантическое пожелание и структурированные ограничения разделены.
- Есть ожидание, три бизнес-исхода, отказ подключения, HTTP 422/503, повтор запроса, индикатор устаревших результатов после редактирования.
- API отвечает синхронно в worker thread FastAPI, не блокируя event loop модельным вычислением.
- Frontend отменяет старый запрос и игнорирует устаревшие ответы; тайм-аут 10 секунд.
- Адрес по умолчанию same-origin для `/app/`; его можно изменить через индикатор подключения. Запросы не содержат секретных ключей.
- CORS разрешён для локальной демонстрации. Для публичного размещения нужны отдельные настройки доступа, лимиты запросов и журналирование.

## Проверка

31 автоматический тест охватывает основной контракт и новые возможности. `evaluation/run_evaluation.py` сравнивает смысловой поиск с простым пересечением слов на 12 ручных запросах, отдельно измеряет пять API-сценариев с повторами. Это диагностический smoke-набор; он не заменяет независимую размеченную выборку, проверку устойчивости к отрицаниям и нагрузочное тестирование.
