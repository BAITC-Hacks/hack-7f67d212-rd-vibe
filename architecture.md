# Архитектура EventMatch

## Поток запроса

```text
Форма пользователя
        │
        ▼
POST /recommend
        │
        ├─► Проверка входных данных и календарного диапазона
        │
        ├─► Есть ли категория в выбранном городе?
        │       └─ нет → category_not_found
        │
        ├─► Жёсткие фильтры
        │       город → категория → дата → формат → бюджет → язык → длительность
        │       └─ никого → no_matches + статистика причин
        │
        ├─► Детерминированное ранжирование
        │       бюджет 70% + текстовые подтверждения 20% + длительность 10%
        │       tie-break: цена, затем id
        │
        ├─► TOP 3
        │
        └─► Доказательное объяснение для каждой карточки
                дата + формат + бюджет + язык/длительность + выдержка из профиля
```

## Компоненты

- `main.py` — HTTP-контракт, бизнес-исходы и сборка ответа.
- `models.py` — Pydantic-схемы и валидация входа.
- `data_loader.py` — однократная загрузка 66 профилей при старте.
- `filters.py` — жёсткие ограничения и счётчики причин отказа.
- `ranking.py` — воспроизводимый скоринг и стабильная сортировка.
- `explanations.py` — генерация двух предложений только из подтверждённых данных.
- `frontend/app.js` — запрос к API, отображение трёх исходов и безопасный резервный генератор объяснения для старой версии backend.

## Почему объяснения не галлюцинируют

Модуль объяснений не обращается к LLM и не создаёт свободный текст. Каждая часть берётся из одного из источников:

- параметры запроса, уже прошедшие фильтр;
- структурированные поля выбранного профиля;
- первая фактическая фраза исходного `description`.

Если профиль попал в выдачу, факт свободной даты следует из проверки `busy_dates`, а формат, язык и длительность — из жёстких фильтров. Сумма резерва вычисляется арифметически из бюджета и `price_from_kzt`.

## Детерминизм

В системе нет случайных чисел, внешних моделей и зависимости от времени. Оценка вычисляется из запроса и профиля. Равные оценки разрешаются сначала ценой, затем неизменным `id`.

## Расширение

Если появится свободное текстовое пожелание пользователя, к ранжированию можно добавить локальные эмбеддинги описаний. Жёсткие фильтры и доказательный слой объяснений при этом должны остаться: семантическая близость не должна возвращать занятого или слишком дорогого подрядчика.
